You are writing test prompts for an OpenClaw skill, following Anthropic skill-creator's eval methodology.

INPUT: the SKILL.md body (already drafted), plus grounding context — usage examples, changelog, and the names of REAL co-resident sibling skills.
OUTPUT: JSON with situated should-trigger prompts AND genuinely-tricky near-miss negatives.

## What makes a good prompt (situated, not test-like)

Write prompts a REAL USER would actually type. Make them concrete and detailed — include realistic specifics: file paths, module/class names, column names or values, model names, error messages, casual phrasing, occasional lowercase/abbreviations. Draw the specifics from the EXAMPLES and CHANGELOG context when present.

- BAD (too short/abstract): "Format this data" / "help me fine-tune a model"
- GOOD (situated): "I've got a train.jsonl of chat transcripts and a 24GB 4090 — walk me through fine-tuning Qwen2.5-7B on it so it stops refusing benign requests. Adapter is fine."

## should_trigger prompts (positives)

- 2-3 prompts.
- At least one must NOT mention the package name directly (tests capability-triggering, not keyword-matching).
- At least one should be an API-migration / version prompt if the CHANGELOG shows breaking changes ("I'm still on the old `X` API, how do I move to …").
- At least one should reflect a realistic task from the EXAMPLES.

## negative_prompts (near-miss negatives) — the hard part

These SHOULD NOT trigger this skill. The valuable ones are near-misses: they share vocabulary or domain with the skill but actually need something else — often one of the SIBLING SKILLS. Do NOT write obviously-irrelevant prompts ("write a fibonacci function" for a PDF skill is useless). Name a sibling library/tool where natural.

- 2-3 near-miss negatives.
- Each must be a plausible request that a careless router might mis-route TO this skill, but that a correct router would send elsewhere.

## functional tests (with/without-skill content check) — write each one as a TRAP for the base model

These grade whether the skill's CONTENT changes the answer. Each test is run WITH and WITHOUT
the skill, so an assertion earns its place ONLY if it would **fail without the skill and pass
with it**. The failure mode to beat: on a well-known library the base model already emits the
obvious-correct answer, so assertions on standard API names pass in BOTH cells and measure
nothing (they get flagged non-discriminating, and lift reads ~0). Defeat this on purpose:

**Method — predict, then trap:**
1. For each prompt, first PREDICT what a competent base model with NO skill would answer.
2. Locate where that prediction is WRONG, INCOMPLETE, or NAIVE — the one thing this skill
   exists to fix: a skipped precondition, a wrong/oversized default, a deprecated API it still
   reaches for, a memory-blowup or silent-correctness gotcha, a required call-ordering. Mine the
   SKILL.md body's pitfalls / gotchas / "common mistakes" content for these.
3. Assert on THAT — not on the parts the base model already gets right.

**Rules:**
- 2-3 tests, each a realistic task prompt whose correct answer HINGES on such a gotcha (reuse/
  adapt the should_trigger prompts). If a prompt's answer has no gotcha the base model would
  miss, it's a weak functional test — pick a different prompt.
- `must_not_contain` is the PRIMARY discriminator and is REQUIRED on every test: name the exact
  wrong / naive / outdated / oversized-default approach the base model reaches for and the skill
  prevents. This is the trap — it's what flips the WITHOUT-skill cell to FAIL.
- `must_contain` / `must_contain_any`: 1-2 exact, NON-obvious substrings the skill-correct answer
  needs — a precise precondition call, a version-correct flag or default value. Do NOT AND
  together several common symbols every answer emits (that fails on phrasing, not on skill value,
  and adds noise, not discrimination). Use `must_contain_any` OR-groups when wording varies.
- `expected_citations`: file / function / flag names the skill's content points to.

- BAD (base model already does all of this → non-discriminating): `must_contain`:
  ["LoraConfig", "get_peft_model", "save_pretrained"] — every base answer names these.
- GOOD (traps the naive default): for "QLoRA a 70B on a 24GB card", `must_contain`:
  ["prepare_model_for_kbit_training"] + `must_not_contain`: ["full fine-tune"] — base answers
  routinely skip the kbit-prep step (breaks the grad path), so the WITHOUT-skill cell fails it.

## mcp_fallback test (ONLY if MCP SERVERS below is non-empty) — graded on tool-firing, not text

If the skill declares an MCP for live docs (see MCP SERVERS), write EXACTLY ONE extra test
that can ONLY be answered by fetching live documentation — a **beyond-references** question the
skill's static SKILL.md + references/ deliberately cannot cover: a very recent release's exact
API, a niche parameter's current default, a version-specific signature. The point is to force
the skill's MCP-fallback path so we can measure whether it actually fires.

- Set `"mcp_fallback": true` on this test. It is graded on whether the agent CALLS the MCP
  (the harness measures the with/without firing delta), NOT on substrings — so `must_contain`
  should be empty or minimal.
- Use `must_not_contain` to catch fabrication when the agent should have looked it up but
  didn't (e.g. a plausible-but-wrong invented flag), if you can name one.
- The prompt must be answerable ONLY via the declared MCP — if the skill's own references
  already contain the answer, it is NOT a valid mcp_fallback case.
- Omit this test entirely if MCP SERVERS is "(none)".
